## Custom CSS Architecture

### Design System as CSS Variables

All shared values live in `styles.css` as custom properties, organised by page theme:

- **Dark theme** (admin, arena, login): `--bg`, `--panel`, `--panel2`, `--border`, `--text`, `--text-muted` with navy palette
- **Light theme** (teacher, student): `--pg-bg`, `--pg-text`, `--pg-muted`, `--pg-border` with parchment palette
- **Card rarity**: `--card-common-bg`, `--card-silver-bg`, etc. as gradient values
- **Leather lock**: `--leather-base`, `--brass`, `--brass-dark`, etc. (login page only)

### Page-Specific Styles

Each HTML page includes its own `<style>` block for layout and page-specific components. This avoids a bloated global stylesheet and keeps styles co-located with their markup.

### Component Class Naming

BEM-inspired naming without the verbosity:
- `.site-header`, `.logo`, `.user-pill`, `.role-badge` — shared
- `.panel` / `.panel--parchment` — modifier for theme variant
- `.btn`, `.btn-gold`, `.btn-outline`, `.btn-danger`, `.btn-sm` — button variants
- `.modal-backdrop`, `.modal`, `.modal--parchment` — modal with theme
- `.poke-card`, `.poke-card--silver`, `.poke-card--prismatic` — card + rarity
- `.scrap-slot`, `.scrap-slot--rot-l`, `.scrap-slot--rot-r` — scrapbook slot + rotation

### Card Rarity System

Rarity is a single data attribute: `[data-rarity="common|silver|gold-rare|prismatic"]`. CSS reads this attribute to apply the correct gradient, border, shadow, and animation. This centralises rarity styling in CSS rather than scattering it across JS string templates.

## Animation Implementation

| Animation | Approach | Complexity |
|-----------|----------|------------|
| Lock open sequence | CSS keyframes + class toggle. 3-phase animation (shackle rise → rotate → fade) triggered by adding `.lock--opening` class on form submit | Medium |
| Dust particles | Canvas 2D, ~50 circles with random drift and sway. requestAnimationFrame loop. Self-contained module | Low |
| Card 3D tilt | mousemove handler calculates cursor position relative to card centre, applies rotateY/rotateX via inline style. mouseleave resets with transition | Low |
| Holofoil sheen | Conic gradient div inside card, transform rotates based on mouse position (same handler as tilt). mix-blend-mode: screen | Low |
| Prismatic hue shift | CSS `@keyframes prismShift` with filter: hue-rotate. Applied via class | Low |
| Star pop sparkle | CSS `@keyframes starPop` on individual star spans. Random position/size generated by JS, animation handled by CSS | Low |
| Card shimmer (touch) | CSS `@keyframes cardShimmerTilt` — predefined rotation sequence. Triggered by class toggle, removed on animationend | Low |
| Modal open/close | CSS transitions on opacity + transform. Class toggle for `.modal--visible` | Low |
| Attack projectile | JS-driven: create div, animate via Web Animations API (translate from attacker to defender position, 0.4s). Remove after complete | Medium |
| Card shake on hit | CSS `@keyframes shake` — 3 x-translate cycles. Applied via class toggle, removed after 0.3s | Low |
| Damage float text | JS: create span, animate via WAAPI (translateY -30px + opacity 0 over 1s). Remove after complete | Low |
| Page load stagger | CSS animation-delay on key elements. Incremental delays (100ms, 200ms, etc.) set via inline style or CSS custom properties | Low |
| Confetti | ~30 divs with CSS `@keyframes confettiFall`. Randomised animation-duration and delay via inline styles. Pure CSS, no JS after creation | Low |
| HP bar transition | CSS `transition: width 0.5s ease` on the fill element. JS only updates the width percentage | Low |
| Math challenge countdown | setInterval (1s), update DOM text. Clear on answer or timeout | Low |
| Tab underline | CSS `transition: all 0.2s` on border-bottom-color | Low |
| Button hover | CSS `transition: all 0.2s` on transform and box-shadow | Low |

### GSAP Assessment

Not needed. All animations are either simple CSS transitions/keyframes or one-off JS-driven effects (projectile, damage text) that the Web Animations API handles cleanly. No complex choreography, scroll-triggered sequences, or timeline dependencies exist.

## State & Logic Plan

### Lock Animation State Machine (Login)

Three states: `CLOSED` → `OPENING` → `OPEN`. Triggered by successful form submission. CSS classes drive the visual phases; a 1200ms setTimeout handles the redirect after the animation completes.

### Card Interaction State Machine

Four modes per card: `IDLE` → `HOVER` (on mousemove) → `FLAT` (on mouseleave) and `IDLE` → `SHIMMER` (on button click) → `IDLE` (on animationend). Hover and shimmer are mutually exclusive — shimmer overrides hover while active.

### Arena Game State Machine

States: `SETUP` → `BATTLE` → `MATH_CHALLENGE` → `RESOLVING` → `BATTLE` (loop) → `GAMEOVER`. Managed with a global `gameState` variable. Each state gates which UI elements are interactive.

### Auth Flow

Already implemented via Supabase. No changes needed — the Auth module pattern works. Only the login page UI (the lock animation) wraps around the existing `Auth.signIn()` call.

### Shared Card Renderer

The `Dashboard.renderCard()` function in `dashboard.js` currently returns an HTML string. It will be refactored to:
1. Accept a card data object + optional size parameter (`'full' | 'mini'`)
2. Generate the correct HTML structure for each size
3. Apply rarity styling via the `[data-rarity]` attribute instead of inline styles
4. Include all holofoil/tilt markup so cards are interactive immediately when inserted into the DOM

The mini card variant (for scrapbook slots) uses the same gradient and border but omits the holofoil layer and image box, keeping only the name, rarity label, and a few decorative stars.

## Other Key Decisions

### Multi-page architecture (no SPA router)

The project has 5 separate HTML files with full page navigations between them. This stays as-is — adding a router would be unnecessary complexity for a project with no client-side routing requirements. Auth state persists via Supabase session across page loads.

### Vanilla JS module pattern (no framework)

The existing code uses IIFE modules (`Dashboard`, `Auth`, `AI`). This stays. The card renderer and tilt handlers are the only shared JS that needs careful organisation. Each page has its own script block for page-specific logic.

### No component system

The project is small enough that a component system (Web Components, template literals, etc.) adds more overhead than value. The card renderer function returning HTML strings is sufficient. If duplication becomes painful, a small template helper (find-and-replace on HTML strings) could be added later.

### Card images from external API

Card character images are generated by Pollinations AI and stored as URLs in Supabase. No local image assets needed except the leather background and favicon.

### Responsive strategy

CSS Grid + Flexbox with a single breakpoint at 700px for major layout changes. The teacher dashboard adds a second breakpoint at 900px for its sidebar collapse. No mobile-first vs desktop-first preference — the existing code uses a mix, and the design documents specify per-component responsive behaviour.
